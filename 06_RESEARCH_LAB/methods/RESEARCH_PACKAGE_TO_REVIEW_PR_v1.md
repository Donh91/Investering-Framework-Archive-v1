## Execution First - owner-directed procedure refinement (2026-11-25)

Within an already authorized material development or research assignment, prefer the largest coherent, reversible, testable work slice that fits the current session and existing owner's scope. Do not split routine internal work into external review requests. This is a procedural refinement of the existing end-to-end method, not a new skill, authority, research admission, release policy or automatic activation of a pilot. On merge, it is available when this method is explicitly selected or otherwise already admitted. Stricter current contracts, actual tool access, due duties, single-writer leases, active-lane caps, read-only windows and safety gates take precedence.

`Research -> Development -> Tests -> Red-team -> Repair -> Retest -> Consolidated delivery -> Required final review -> Governed release -> Consumer/effect readback`

### Internal work loop

1. **Research:** resolve the original owner, exact current source, competing PRs, scope, source/legal clocks, prior falsifications, smallest strong baseline and observable acceptance. Freeze the question and failure matrix before evaluating outcomes. Read only relevant dependencies, not the entire archive every time.
2. **Development:** if permitted, implement the smallest complete vertical slice in the original owning branch or an explicitly isolated non-default branch. Include producer, consumer and regression implications in the same coherent delivery where ownership permits. For a novel scientific candidate awaiting admission, limit work to authorized local non-outcome prototypes, source qualification and test preparation; never use implementation to circumvent scientific adjudication or active-lane limits. A reproduced defect whose owner requires Codex intake still follows that intake; prepare the useful patch/test evidence locally if permitted rather than simply relay it. Read-only actors may investigate, reproduce and package within their actual authority, not write or run restricted work.
3. **Tests:** run actual targeted unit, integration and existing relevant regression tests where tools and data permit. Record commands, exact source/preimage and candidate identities, inputs, pass/fail counts and omissions. A test specification is not a test run. Fixtures, historical replay, independently admitted prospective evaluation and natural runtime evidence are distinct.
4. **Red-team:** use existing research-lab-red-team and relevant owner methods. Attack missing/stale/future inputs, malformed values, boundary cases, contradictions, leakage, duplicate events, replay, error paths and unintended downstream effects as applicable. Use an independent mathematical/behavioral oracle or negative control where possible; test guard-removal mutants for consequential guards. This is AUTHOR_SELF_CHECK, not independent review, even if different prompts or internal reasoning passes are used.
5. **Repair and retest:** fix discovered in-scope defects before requesting external review. Re-run failing cases and impacted regression tests on the resulting candidate; preserve failed attempts and unresolved P0/P1 findings. Continue until acceptance is met, evidence falsifies the proposal, a real scope/authority/source gate stops it, or the current execution budget/tool limit is reached. Do not loop unchanged attempts or optimize test results at the expense of correctness.
6. **Consolidated delivery:** before ending the session, provide actual changed paths/diff or executable artifact, exact immutable source/candidate references, test and counterexample receipts, residual risk, rollback or original-owner next action. Prefer one reviewable original PR for one coherent authorized slice, not an artificial omnibus PR or one PR per trivial substep. No review request on an unstable head merely to show activity. If a lane is blocked, complete independent permitted parts and retain exact resume checkpoint. Do not promise invisible work after the session.
7. **Required final review:** request the minimum admissible independent review on the completed exact head or at the existing science/admission boundary. Earlier independent approval remains mandatory where the original policy requires it before implementation, outcome access, expenditure or high-impact change. The purpose is to avoid unnecessary intermediate reviews, not to waive any required review. One consolidated review request may refer to a coherent package; never reuse stale approval for changed content or assume one PR's review covers another. Follow current AGENTS.md and S1 REVIEW_ADMISSION.md; no self-approval, fake independent review, policy downgrade, or bypass. Resolve adverse findings and retest; obtain fresh required review for changed head. If waiting, progress unrelated already-authorized non-overlapping work, not another status comment.
8. **Closure:** after the existing release gates, read back merge/main and the real producer/consumer. Observe actual effect under original scientific admission, never equate tests, PR, or merge with runtime adoption or economic edge.

### One compact receipt in existing owner artifact

Include only new material evidence: owner + objective; authority and scope; source/candidate SHA or exact local hash; artifact/diff; tests EXECUTED versus PROPOSED and failures; self-red-team and repairs; remaining independent gate and why it is required; next actionable trigger or verified consumer. Keep intermediate scratch work internal. If no meaningful delta, close as appropriate or return no-op; do not generate repeated reports.

### Measure improvement, not activity

Use existing original-owner receipts / Agent Invocation Contribution Ledger when a qualified join is available. Compare matched complexity and permission cohorts for elapsed time to useful artifact and verified closure, number of avoidable intermediate handoffs, completed internal work, rework after review, escaped critical defects, coverage and actual token/cost where known. Count blocked/no-op and unsuccessful cases; never optimize PR count, lines changed, review count alone, or self-reported progress. No new ledger or task. Static acceptance is not evidence of real agent adoption. The existing independent skill-quality-gate remains responsible for any default-scope promotion or performance claim. Narrow or retire this refinement if it worsens review quality, safety or P0 latency.

## Stage 1: source evidence and falsification

For each material claim classify FACT / SOURCE_REPORTED / INFERENCE / HYPOTHESIS / PERFORMANCE_CLAIM / UNVERIFIED. Attach authoritative URL or Git commit and blob, originally published versus first-known times, capture/availability/revision clocks, venue/quote/units, scope, limitations, missingness, and license of reusable third-party code. User screenshots, X marketing and derived provider charts are hypotheses, not point-in-time data.

Challenge the claim before advocating it. Name the strongest opposing evidence and cheapest valid mechanical baseline, with equal clock, venue, target, horizon and eligible cases. Separate explanation of a historical event from a forward-visible predictor, statistical outcome and actionable economic gain. Detect overlapping episodes, many correlated signals, confidence inflation, feature vintage leakage, post-hoc tuning, abandoned attempts and survivorship. Check risk of delayed warnings versus false warnings and the price of missed opportunities. If a feature cannot change one defined decision against a simpler incumbent, classify EXPLANATORY_ONLY or REJECT.

Mandatory adversarial check for surprising claims: use existing research-lab-red-team skill and, when materially relevant, one bounded conclusion-challenge-loop. These are internal methods when applied by the author, not independent evidence or a substitute for the existing independent scientific/admission/release gate. Neither skill may promote its own hypothesis or permit trading.

## Stage 2: actual bounded research work

Create one small research question packet, not a new central registry: original issue, hypothesis, falsifier, simplest comparator, source and exact as-of/first-known cutoff, target, method, unit/episode, data class, abstentions, sample size versus effective independent N, expected safety/economic endpoints, cost ceiling, stop and next trigger. Freeze before new prospective observations. Never recast already-seen W46/W47 outcomes as held-out proof.

Split into 2-10 genuinely independent lanes only when warranted, under existing research-parallel-lanes; otherwise execute serially. Source vintage/availability qualification MUST precede tests; validation MUST precede product conclusion. Real concurrency means independent tool calls, independently verified GitHub Actions jobs or authorized AI-agent runs, with run ID, SHA, logs, byte/digest and conclusion. A list of planned tracks is not multi-agent execution. Default paid spend USD0. Existing authorized automation is not controlled merely by writing it in a document.

Run reproducible public-safe controls first: price persistence/no-change, honest existing production comparator, ATR/volatility where pre-registered, negative/placebo controls, block/episode-aware uncertainty, real missingness, venue parity, UTC closed bars, and complete originally issued cohorts. Avoid fitting to the very crash that motivated the question. For registered tests consult prospective-evidence-ledger; no newly invented test IDs or scores. Source and result failures remain visible; halt only affected lanes, not unrelated independent reads.

## Stage 3: synthesis and scientific decision

Produce a compact but sufficiently detailed report with:
- original question and practical changed decision;
- source-by-source provenance and strong countercase;
- valid/invalid/unknown original observations and denominator;
- smallest baseline and any measured incremental evidence;
- costs and false-negative opportunity cost;
- exact surviving/falsified/blocked hypothesis;
- ONE primary new actionable delta, original issue and smallest reversible action;
- what was actually executed, file/blob/PR/CI/run and what was not.

## Pilot evaluation and anti-failure cases

Before making this method default, an independent reviewer/skill-quality-gate must compare baseline skill and candidate on these test cases, retaining exact input/evidence and requiring an explicit output check:
- POSITIVE: new thread asks for deep original research with a reviewable PR, GitHub write authorized, no duplication.
- POSITIVE: existing bounded code defect should route to original Codex intake, never invented CODEX_READY.
- NEGATIVE: routine simple status and ordinary short market question should not spawn research mission.
- NEGATIVE: prior open PR covers the same claim; no duplicate.
- NEGATIVE: unavailable restricted source; no public data leak or fake first-known.
- NEGATIVE: Round 3 collection only; no hypothesis/effect/PnL tests.
- NEGATIVE: new expensive API desired, but no exact one-shot provider/budget consent; no payment.
- NEGATIVE: bot favorable COMMENTED not formal APPROVED; don't report release PASS.
- NEGATIVE: changed HEAD after review and CI, invalidate finality.
- NEGATIVE: site/consumer still UNAVAILABLE; code merged is not integrated/economically proved.
- NEGATIVE: connected GitHub is read-only; no fabricated PR or background automation.

Quality criterion: exact citations and sources, correct new issue/PR routing, no new permissions, reduced duplicated research, one actual owner action, no false "done". STATIC_ONLY verifies documentation semantics; only real blinded repeatable use could show time-to-closure gains. Trim/retire the extension if it adds loops or delays P0 completion.
