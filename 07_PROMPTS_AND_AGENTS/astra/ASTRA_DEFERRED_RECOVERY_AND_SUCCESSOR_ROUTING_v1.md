# Astra Deferred Recovery and Successor Routing v1

Status: `ACTIVE_DISCOVERY_AND_REQUALIFICATION_CONTRACT`

## Purpose
Prevent valuable framework research and implementation from remaining stranded merely because an older owner, README, issue, mission card, queue item, or research package was written as `ASTRA`, `ASTRA_READY`, `DEFERRED_FOR_ASTRA`, frontier-model work, or otherwise assumed a future Astra-class executor.

This is not a new engine, forecast authority, scientific authority, merge authority, or parallel queue owner. It is a recovery and requalification procedure layered on the existing repository owners, `research/api_agent/CAPABILITY_ROUTING_POLICY_v1.json`, `research/api_agent/API_TASK_REGISTRY_v1.json`, Codex governance, and current issue/domain ownership.

## Governing rule
`ASTRA_RESERVED` MUST NOT mean `WAIT_FOR_ASTRA` by default.

Every discovered deferred item must be re-evaluated against the best currently available qualified execution lane. If current Sol, Terra, Luna, deterministic tooling, Codex, or a bounded combination can complete the task safely and to the required evidence standard, execute through that existing lane. Escalate to Astra only when a concrete capability requirement remains unsatisfied after decomposition/requalification.

Model identity never grants authority.

## Required discovery surface
Start from fresh `main` and resolve normal repository precedence before acting. Discovery is semantic, not keyword-only. Inspect at minimum:

1. `AGENTS.md` and archive-control precedence/authority owners.
2. `07_PROMPTS_AND_AGENTS/astra/`, including mission pointers, landing-zone policy, research missions and repository mission router.
3. `research/api_agent/`, especially capability routing, task registry, budget policy, runtime qualification and compounding-learning owners.
4. Current `LATEST_*` handoffs, remediation queues, Codex-ready queues and execution state referenced by the repository mission router.
5. Open GitHub issues and PRs that own research, remediation, architecture or deferred work.
6. Domain README mission cards and research readiness/status files across framework roots.
7. Historical wording equivalent to: Astra, frontier model, deferred, future model, deep research, advanced reasoning, blocked on model capability, revisit when stronger model exists, manual-only due model limitation.

Do not assume absence of the word `Astra` means absence of Astra-deferred work.

## Requalification ladder
For each candidate, first resolve the existing canonical owner and dependencies. Then classify the smallest bounded work unit:

- `DETERMINISTIC` - parsing, validation, hashes, schema checks, mechanical inventories and reproducible calculations where no model judgment is needed.
- `LUNA` - low-risk classification, extraction, summarization and structured triage.
- `TERRA` - synthesis, conflict review, evidence normalization, documentation and bounded research where Terra satisfies the task profile.
- `SOL` - difficult reasoning, deep research, architecture review, scientific critique, cross-document synthesis, adversarial review and complex planning where Astra-specific capability is not demonstrated.
- `CODEX` - repository code/file implementation only under existing write/task authority, followed by required independent review.
- `ASTRA_ESCALATION` - only when the task has a documented residual requirement that qualified lower lanes cannot safely satisfy after reasonable decomposition.

Prefer the cheapest qualified executor, not the cheapest model regardless of capability.

## Mandatory anti-stranding behavior
Discovery is not completion. An agent must not stop after producing a list of deferred tasks when one or more items are executable under existing authority.

After inventory and dependency resolution:

1. Deduplicate aliases and competing mission descriptions against existing owners.
2. Remove tasks already completed, superseded, invalidated or blocked by a real external dependency.
3. Requalify remaining work using current model/runtime capability rather than historical labels.
4. Prioritize executable work by `impact × readiness × unblock_value ÷ expected_cost_and_risk`.
5. Execute one bounded high-value unit to verified completion before opening another large unit, unless existing governance explicitly supports safe parallelism.
6. Persist evidence/receipts through the existing owner and queue mechanisms.
7. Continue to the next eligible item while budget, authority and runtime gates remain satisfied.

Do not create a second forecast engine, scientific adjudication engine, remediation owner, task registry, or merge path.

## Candidate states
Use existing registries where they can express the state. If a recovery view is required, it is derived/non-authoritative and should map candidates to:

- `DISCOVERED`
- `OWNER_RESOLVED`
- `READY_DETERMINISTIC`
- `READY_LUNA`
- `READY_TERRA`
- `READY_SOL`
- `READY_CODEX`
- `RUNNING`
- `BLOCKED_DEPENDENCY`
- `ASTRA_ESCALATION_REQUIRED`
- `VERIFIED_DONE`
- `SUPERSEDED`
- `REJECTED`

Every `ASTRA_ESCALATION_REQUIRED` item must include the concrete unsatisfied capability, evidence of attempted/decomposed lower-lane qualification, and the smallest remaining Astra-shaped unit. Historical wording alone is insufficient.

## Context and cost discipline
Follow least-privilege context. Do not repeatedly feed the entire repository to expensive models. Resolve owners and source refs deterministically first, then provide bounded evidence packs to the selected model.

Use caching/reusable stable context where supported by the existing API architecture. Prefer deterministic/Luna/Terra preprocessing before Sol when it reduces context without losing decision-relevant evidence.

Budget authority remains with the existing API budget owner. This contract does not raise any hard stop. When budget is constrained, preserve highest-information-value executable work and leave a precise resumable receipt rather than starting many partial missions.

## Completion standard per recovered task
A recovered task is not `VERIFIED_DONE` because a model produced prose. It must satisfy the original owner's completion semantics, including applicable source provenance, deterministic tests, schema validation, hash/readback, independent review, PR/CI evidence, or research-adjudication gates.

## Astra use
Astra remains valuable for genuinely frontier-shaped units, especially unresolved cross-domain architecture/orchestration or research where Sol fails the required quality/capability gate. Astra should receive the smallest residual hard problem after lower-cost preparation, not the full unfiltered repository backlog.

## First recovery mission
Run a fresh-main census of currently live or deferred Astra/frontier-model work across the discovery surface above. Produce a deduplicated owner-bound inventory, requalify each item to the current cheapest qualified lane, identify the highest-value immediately executable Sol/Terra/Deterministic/Codex work, and begin execution under existing authority. Do not wait for Astra merely because the historical mission name contains Astra.
