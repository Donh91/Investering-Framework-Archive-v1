## Recovery method, follow in this order

**A. Diagnose before retry.** Record the original failure fingerprint, affected subsystem, earliest source evidence and the exact reproducible failure or conflict. Inspect historical blobs, the merge base and the newest main, not just PR comments or titles. Distinguish a changed code/data root cause from a repeated description of the same symptom. After two materially identical failed attempts without fresh evidence, stop unchanged retries and classify `PROCESS_STALLED` with a different bounded route.

**B. Repair only the owner-controlled scope.** On an existing original PR branch, prefer a minimum reproducible patch that preserves newer main content and ownership. Before conflict resolution inspect BOTH sides and the merge base. Never resolve conflict using an unexamined blanket ours/theirs strategy. Use an explicitly verified non-default branch for writes. Preserve source and recovery separation and prevent simultaneous HEAD writers. If a branch is closed/merged, never reopen or rewrite it merely to claim another fix; route a genuinely remaining defect to its existing owner.

**C. Test the falsifier.** Define the failing positive case and adversarial negatives BEFORE proposing final integration. Require relevant unit tests, a test that would fail if the repaired guard were removed, cross-module integration tests when warranted, and current exact-HEAD CI. Avoid an unchanged all-green test suite being mistaken for proof that the defect was repaired.

**D. Separate three completions.** (1) Code patch accepted: actual changed bytes on a native GitHub branch + tests; (2) original PR merged: GitHub native merged state, exact approved SHA and new main blob readback; (3) defect closed: independent natural producer/consumer or Pages readback AFTER the merge, or a scientifically legitimate terminal rejection/supersession. Do not collapse these stages. Green CI, a reviewer comment, a model patch, a task wake, a manually merged sibling PR and a label are NOT evidence of S1 executing or completing the original repair.

**E. Decide and move on.** For each original PR record exactly one of `READY_TO_MERGE` (advisory, `authorized=false`), `IN_REPAIR`, `BLOCKED_WITH_TRIGGER`, `PROCESS_STALLED`, `POST_FIX_OBSERVATION`, `CLOSED_VERIFIED` or `SUPERSEDED_VERIFIED`, with evidence and a reactivation trigger where applicable. Respect 4 material-touch SLA, max 3 distinct PR candidates/run, and move to an independent candidate when one is legitimately blocked. Do not create a new supervisor/schedule or release without the existing explicit owner authorization and live platform gates.

**F. Learn from verified outcomes.** Link the GitHub source commit, PR, exact changed blob SHAs, root cause, negative-control test, merge receipt, postmerge producer evidence and residual failure to the EXISTING operational-memory and incident owner. Do not manually forge generated LATEST pointers or an immutable episode. If the producer cannot ingest the episode, record a scoped implementation defect with that owner, not a claim that learning occurred. Revalidate the old method against current code whenever it is reused. A reusable candidate is `CANDIDATE_ONLY` until independent `skill-quality-gate` evaluation and governed registry promotion. Never let this skill self-score, self-promote or change release permissions.
