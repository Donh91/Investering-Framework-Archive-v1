For a user in a new ChatGPT thread requesting a thorough, original research package that should proceed to a reviewable GitHub PR or real product integration. The outcome must be one of: REJECT / DEDUP / SOURCE_BLOCKED / review-ready research PR / governed code-repair PR / implementation PR and verified actual consumer. A future thread cannot work silently after it ends unless an existing scheduled task or actual connector action is independently available and authorized.

## Stage 1: source evidence and falsification

For each material claim classify FACT / SOURCE_REPORTED / INFERENCE / HYPOTHESIS / PERFORMANCE_CLAIM / UNVERIFIED. Attach authoritative URL or Git commit and blob, originally published versus first-known times, capture/availability/revision clocks, venue/quote/units, scope, limitations, missingness, and license of reusable third-party code. User screenshots, X marketing and derived provider charts are hypotheses, not point-in-time data.

Challenge the claim before advocating it. Name the strongest opposing evidence and cheapest valid mechanical baseline, with equal clock, venue, target, horizon and eligible cases. Separate explanation of a historical event from a forward-visible predictor, statistical outcome and actionable economic gain. Detect overlapping episodes, many correlated signals, confidence inflation, feature vintage leakage, post-hoc tuning, abandoned attempts and survivorship. Check risk of delayed warnings versus false warnings and the price of missed opportunities. If a feature cannot change one defined decision against a simpler incumbent, classify EXPLANATORY_ONLY or REJECT.

Mandatory independent check for surprising claims: use existing research-lab-red-team skill and, when materially relevant, one bounded conclusion-challenge-loop. Neither skill may promote its own hypothesis or permit trading.

## Stage 2: actual bounded research work

Create one small research question packet, not a new central registry: original issue, hypothesis, falsifier, simplest comparator, source and exact as-of/first-known cutoff, target, method, unit/episode, data class, abstentions, sample size versus effective independent N, expected safety/economic endpoints, cost ceiling, stop and next trigger. Freeze before new prospective observations. Never recast already-seen W46/W47 outcomes as held-out proof.

Split into 2-10 genuinely independent lanes only when warranted, under existing research-parallel-lanes; otherwise execute serially. Source vintage/availability qualification MUST precede tests; validation MUST precede product conclusion. Real concurrency means independent tool calls, independently verified GitHub Actions jobs or authorized AI-agent runs, with run ID, SHA, logs, byte/digest and conclusion. A list of planned tracks is not multi-agent execution. Default paid spend USD0. Existing authorized automation is not controlled merely by writing it in a document.

Run reproducible public-safe controls first: price persistence/no-change, honest existing production comparator, ATR/volatility where pre-registered, negative/placebo controls, block/episode-aware uncertainty, real missingness, venue parity, UTC closed bars, and complete originally issued cohorts. Avoid fitting to the very crash that motivated the question. For registered tests consult prospective-evidence-ledger; no newly invented test IDs or scores. Source and result failures remain visible; halt only affected lanes, not unrelated independent reads.

## Stage 3: synthesis and scientific decision

Produce a compact but sufficiently detailed report with:
- original question and practical changed decision;
- source-by-source provenance and strong countercase;
- valid/invalid/unknown original observations and denominator;
- smallest baseline and any measured incremental evidence;
- costs and false-negative opportunity cost;
- exact surviving/falsified/blocked hypothesis;
- ONE primary new actionable delta, original issue and smallest reversible action;
- what was actually executed, file/blob/PR/CI/run and what was not.

The existing Research Lab #1512 receives a source/overlap intake. Existing Strategist #1157 gives its actual allowed decision: REJECTED_FALSIFIED / DEDUPED_TO_EXISTING_OWNER / SOURCE_BLOCKED_WITH_TRIGGER / PROSPECTIVE_COLLECTION_ONLY / FORWARD_TEST_PREREGISTERED / APPROVED_FOR_IMPLEMENTATION_REVIEW / NOT_DECISION_USEFUL. The research author may propose a verdict, but cannot impersonate #1157 or convert an issue comment into test activation.

## Stage 4: choose output, never force a PR

- NO_PR if duplicate, no value or blocked from a meaningful next action; provide exact original owner/trigger.
- RESEARCH_PR for one concise, source-bound read-only implementation-grade plan on isolated task branch. It is not permission to change code, research budget, market signal or schedules.
- PROSPECTIVE_PROTOCOL only with original registered owner, future pre-outcome freeze and separate source/first-known gate, never backdated.
- CODE_REPAIR_CANDIDATE only if a specific code defect is reproduced. Read .agents/skills/codex-intake/SKILL.md; freeze failing case and high-risk negative/mutation tests, submit under existing candidate schema. Only the existing maturation controller can declare CODEX_READY.
- IMPLEMENTATION_PR only after owner approves the bounded code/data/consumer contract. Implement inside existing original owner and files; smallest reversible code diff, robust negative/positive/mutation tests. A new scheduler, model, wallet, scanner, credential, policy or writer is NOT an acceptable shortcut to a finished task.

Before any write apply .agents/skills/archive-governance/SKILL.md. Use existing verified non-default task branch; no direct main, no placeholder probe files, no backup/Vault action from this method. PR text includes original owner and evidence, exact head/base, complete change list, risk classification, expected tests, privacy and no-trade boundary. Code output and research summary remain distinct. P0/P1/P2 scientific uncertainty is not automatically a code defect.

## Stage 5: independent exact-head review, proper merge and real consumer

Codex can review eligible non-Codex LOW/MEDIUM original PRs, Claude the Codex-authored/HIGH paths under current repository rules. A Codex “no major issues” comment is not a formal approved review when the gate requires APPROVED. HEAD modification resets review finality. Verify all native exact-head required CI, complete diff, source/privacy check, no unresolved critical findings, proper branch classification, latest main and current S1 release rules. Public site/.github may be HIGH even if a PR claims MEDIUM. An explicit owner mandate is not permission to skip a mandatory safety control.

S1 #1156 may route or release only as its existing live policy permits; a chat owner-present merge is never represented as S1 autonomous merge. For any allowed merge use squash and expected-head; then verify new main SHA and every changed blob. Separate this code completion from the real adoption: website actually displays the original forecast/score with provenance; private Alpha consumes approved readonly public regime as-of hash and handles stale/unknown; no private value flows back to public. Read natural native run receipts and real consumer output. If no consumer evidence, state MERGED_BUT_NOT_RUNTIME_VERIFIED.

Subsequent outcomes may be scored only by their pre-registered original owner when true source maturity and valid holdout are established. Record actual benefit/regression against frozen baseline, including abstentions, false alarms, opportunity cost and data coverage; otherwise EFFECT_UNPROVEN. No self-promotion. Closure means VERIFIED_CLOSED, FALSIFIED, DUPLICATE_CLOSED or BLOCKED_WITH_EXPLICIT_TRIGGER, with exact original owner and observable unblocking event; avoid repeated identical work and “just watch” parking.

## Pilot evaluation and anti-failure cases

Before making this method default, an independent reviewer/skill-quality-gate must compare baseline skill and candidate on these test cases, retaining exact input/evidence and requiring an explicit output check:
- POSITIVE: new thread asks for deep original research with a reviewable PR, GitHub write authorized, no duplication.
- POSITIVE: existing bounded code defect should route to original Codex intake, never invented CODEX_READY.
- NEGATIVE: routine simple status and ordinary short market question should not spawn research mission.
- NEGATIVE: prior open PR covers the same claim; no duplicate.
- NEGATIVE: unavailable restricted source; no public data leak or fake first-known.
- NEGATIVE: Round 3 collection only; no hypothesis/effect/PnL tests.
- NEGATIVE: new expensive API desired, but no exact one-shot provider/budget consent; no payment.
- NEGATIVE: bot favorable COMMENTED not formal APPROVED; don't report release PASS.
- NEGATIVE: changed HEAD after review and CI, invalidate finality.
- NEGATIVE: site/consumer still UNAVAILABLE; code merged is not integrated/economically proved.
- NEGATIVE: connected GitHub is read-only; no fabricated PR or background automation.

Quality criterion: exact citations and sources, correct new issue/PR routing, no new permissions, reduced duplicated research, one actual owner action, no false "done". STATIC_ONLY verifies documentation semantics; only real blinded repeatable use could show time-to-closure gains. Trim/retire the extension if it adds loops or delays P0 completion.
